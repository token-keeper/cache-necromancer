# 작업 인수인계 — cache-necromancer v0.3.0 트랙 (asyncRewake 기반 architecture)

> 2026-05-15 진단 세션 종료 시점. v0.2.2 의 fundamental 결함 ([[cache namespace 분리]]) 의 진짜 fix 가 Claude Code hook 의 `asyncRewake` 메커니즘으로 확정. 외부 fire 자체 폐기 + daemon 폐기 + 코드 ~95% 삭제 예정.

## 한 줄 요약

cache-necromancer 의 v0.3.0 은 **architecture 전환**: 별도 daemon 이 `claude -p` 로 외부 fire 하던 방식 → Claude Code 의 native hook (`asyncRewake`) 으로 chat 세션 내부에서 self-wake. cache prefix 가 byte-exact 보존되어 진짜로 cache TTL refresh 가능.

### 2. Test 1~8 — cache namespace 분리 확정
자세한 evidence: `docs/handoff/archive/2026/Q2/2026-05-15-v0.2.2-cache-investigation.md`

핵심: `claude -p` mode 의 system prompt 와 chat mode 의 system prompt 가 byte 단위로 다름. Anthropic prompt cache 는 prefix hash 기반이므로 system 부터 다르면 cache breakpoint 가 분리됨 → fire 가 chat cache 를 절대 refresh 못 함.

Test 8 의 정확한 수학:
- chat turn 5 의 cache_read = 17,601 (chat system) + 25,102 (chat turn 1 cache) = 42,703 → fire turn 4 의 cache 무시
- fire #2 의 cache_read = 18,833 (-p system) + 27,476 (fire #1 cache) = 46,309 → fire 끼리만 hit

→ 두 모드가 완전 분리된 cache pool. PR #11 의 fix 들 옳지만 fundamental 문제 해결 못 함.

### 3. Anthropic prompt cache docs 조사 (방금)
docs: https://platform.claude.com/docs/en/build-with-claude/prompt-caching

- TTL 은 **sliding window** — cache hit 마다 refresh, 추가비용 0 (refresh = 0.1× base = $0.50/MTok for Opus)
- cache hit 조건: tools+system+messages 전체 prefix 의 **100% byte-exact match**
- cache 격리 범위: **organization/workspace 레벨** (sid 무관) — 같은 workspace 면 누가 보내든 hit
- 1h cache 는 `cache_control.ttl="1h"`
- lookback: breakpoint 부터 최대 20 block (단 prior write 있어야)

→ **cross-process refresh 가능** (도구 가정 자체는 옳음). 문제는 `claude -p` 가 다른 system 을 주입한다는 것뿐.

### 4. fix 후보 평가 (A~G)
- A `claude -c` interactive — 자동화 어려움
- B Anthropic API 직접 호출 — chat prefix byte-exact 재현 필요. JSONL 만으론 부족 (dynamic system sections)
- C fork 빼고 + UI hide — cache namespace 분리 그대로
- D `-p` system 을 chat 과 동일하게 — claude binary 가 Mach-O native (Node.js 아님), undocumented flag 없음. 10-20%
- E Anthropic docs 조사 (완료)
- F 도구 폐기 — 가정 옳으므로 부적합
- G HTTPS proxy capture + replay (Codex 추천) — 65% 확신, 3-5시간 작업
- **H Stop hook + asyncRewake** (사용자 제안 + claude-code-guide 처음에 부정 → Codex 가 asyncRewake 메커니즘 지적 → docs 직접 확인으로 확정)

## 알려진 issue / 미해결

1. **settings hot-reload 안 됨** — settings.local.json 변경 후 claude 재시작 필요. `claude -c` resume 시 cache 만료됐으면 첫 wake 가 rebuild 비용
2. **Multiple Stop hook fire (race 아님 — 정정)** — 이전 추정 ("동일 turn 에 hook 2회 발화 race") 은 잘못됨. POC B + jsonl 타임라인 분석 결과 사용자가 같은 chat 에 user input 을 두 번 빠르게 보낸 것이 원인 (매 user turn 마다 Stop hook 정상 fire). Claude Code 내부 race condition 이 아니라 사용자 동작 그대로 반영된 정상 동작. 처리: timestamp 비교 (latest_fire 만 wake) 로 충분. sleep 자체가 throttle 역할이라 wake-after-wake 무한 루프 차단도 불필요
3. **UI noise**: wake-up turn 영구 transcript 기록. UI 는 reminder body hide 하고 `task-notification` summary "Stop hook feedback" + 모델 응답 ('ok', '2') 만 visible
4. **무한 루프 방지**: wake-up turn 끝 → 또 Stop hook → 무한. marker 또는 timestamp 차단 필요
5. **wake latency**: 큰 ctx wake-up API call 1m+ 사례 (cache hit 라 비용은 작지만)
6. **Claude 가 reminder 보고 분석/tool 사용 위험**: prompt 명확히 "Reply only ... No tools, no analysis" 명시했음에도 가끔 tool 사용 (cc=2,646 turn 에 Write+Bash 1회씩) — production 디자인 시 prompt 정교화 필요

## v0.3.0 architecture 제안

### 폐기 대상
- `daemon/` 전체 (refresh.py, subprocess fire 로직, lock, idle shutdown)
- `lib/config.py` 의 daemon 관련 옵션 대부분 (fire_timeout, idle_shutdown, etc.)
- subprocess fire 회귀 가드 16개 (PR #11) — 의미 사라짐
- `~/.cache-necromancer/` 의 daemon 관련 file (lock, state, log 등) — 일부 또는 전체

### 유지 / 신규
- 도구 본체: hook config 자동 등록 + sleep script + marker 관리
- Claude Code settings 의 hook 항목 자동 install/uninstall 명령 (예: `cn install`, `cn uninstall`)
- `cn status`: 현재 hook 등록 상태 + 마지막 wake 시각 + cache 추정 만료 시각
- 핵심 결정 항목:
  - **sleep duration**: 5분 cache 갱신 (~270s) vs 1h cache 갱신 (~3000s = 50분)?
  - **reminder 본문 최소화**: empty body 시 모델 반응? `echo "" >&2; exit 2` 가능성
  - **race condition 처리**: marker file timestamp + ttl, 또는 다른 메커니즘
  - **사용자가 wake 대기 중 새 prompt 입력 시 동작**: 어떻게 되는지 검증 필요

### 도구 정신 재검토

기존 정신:
- 자리 비울 때 cache 만료 비용 폭증 방지

새 정신 (변경 없음):
- 동일. 단 메커니즘이 외부 fire → 내부 self-wake 로 전환

이름 적절성:
- "cache-necromancer" = 죽은 cache 살리기. asyncRewake 는 살아있는 cache keep-alive. 약간 어긋남. 단 이름 변경은 큰 작업이므로 보류
