# cache-necromancer 진단: fire 와 chat cache 의 namespace 분리

> 2026-05-15 v0.2.2 진단 세션 결과 정리. **`docs/handoff/2026-05-15-v0.2.2-fire-tty-rootcause.md` 의 결론은 잘못됐음** — 그 doc 은 진단 중간 단계의 fork claude 가 자동 생성한 것으로, fundamental 결론이 이번 진단으로 정정됨.

## 진단 목적

cache-necromancer 의 핵심 가설 검증:
- 도구 목적: 사용자가 1시간 후 chat 재개 시 cache_create 안 되게 fire 가 chat 의 prompt cache TTL 갱신
- 가설: `claude -p --resume <sid>` 발사 → 사용자 chat 의 cache TTL 갱신
- 검증 필요: fire 의 cache 가 chat 의 다음 turn 에서 hit 되는지

## 테스트 timeline

### Test 1 — 진단 세션 (1M context) subprocess fire (capture_output=True)
**환경**: 활성 사용자 chat sid `b29c7a45...` 으로 `subprocess.run(capture_output=True)` fire 발사.

**결과**:
- 90초 silent hang
- stdout/stderr **둘 다 0 byte**
- exit code: None (timeout)

**의미**: PIPE 환경 + 큰 transcript + 활성 sid self-resume = silent hang. 데몬 환경과 동일.

### Test 2 — 진단 세션 subprocess fire (file redirect)
**환경**: 같은 조건, PIPE 대신 `stdout=open(file, 'wb')`.

**결과**: 동일 (0 byte, 90초 hang)

**의미**: PIPE buffering 문제 아님. 더 깊은 이유 (큰 transcript + 활성 sid + non-tty).

### Test 3 — 진단 세션 fire (script tty + fork 빼고 + 능동 prompt)
**환경**: `script` 명령으로 fake tty, `--fork-session --no-session-persistence` 제거, `-p "."` (능동 prompt).

**결과** (195초):
```
duration_ms       = 195,295
num_turns         = 7              ← fork claude 가 능동 작업
cache_read        = 1,110,993      ← 7 turn 누적
cache_creation    = 205,427        ← 큰 cache build
total_cost_usd    = $2.06
```

**의미**:
- tty 환경 + 능동 prompt → fork claude 가 메모리 파일 + handoff doc 자동 작성 (의도치 않은 부작용)
- 비용 폭증 ($2.06)
- `docs/handoff/2026-05-15-v0.2.2-fire-tty-rootcause.md` 가 이 시점에 자동 생성됨

### Test 4 — 진단 세션 prompt 변경 (수동 stop 명령)
**환경**: `-p "Cache refresh ping. Reply 'ok' in one word. Do not use any tools. Do not analyze prior context."`

**결과** (17초):
```
duration_ms       = 17,136
num_turns         = 1              ← 능동 작업 차단 성공
cache_read        = 18,833         ← 안정 prefix 만 hit
cache_creation    = 213,607        ← 여전히 큰 build
total_cost_usd    = $1.35
```

**의미**:
- prompt 변경으로 능동 작업 차단 ✓
- 시간 195s → 17s ✓
- 부작용 차단 ✓
- 단 cache_creation 213K — 진단 세션 transcript 크기 (1M) 와 비례

### Test 5 — Desktop 세션 fire (작은 transcript, fork 빼고)
**환경**: 새 작은 chat (`738042e5...`), fork-session 제거.

**결과 1** (fire #1, "Cache refresh ping..."):
```
cache_read     = 18,833            ← 동일 안정 prefix (Test 4와 정확히 일치)
cache_creation = 27,131            ← Desktop transcript 크기
duration       = 2초
cost           = $0.18
```

**결과 2** (chat 의 다음 turn — "테스트"):
```
cache_read     = 44,734            ← 17,601 + 27,131 hit
cache_creation = 37                ← 거의 없음
```

이때 **44,734 ≈ chat system 17K + fire 의 cache 27K**. 표면적으로는 fire cache 가 chat 에 hit 된 것처럼 보임. **잘못된 결론 도출**: "도구 fundamental 정상 작동".

### Test 6 — Desktop fire #2 (`-p "1+1="`)
**환경**: 같은 Desktop 세션에 fire 두 번째.

**결과**:
```
cache_read     = 46,005            ← 거의 전부 hit
cache_creation = 0                 ← 완전 hit
cost           = $0.023            ← fire #1 의 1/8
```

**의미**: fire 끼리는 cache 100% hit. 두 번째 fire 부터는 비용 매우 작음.

### Test 7 — 새 세션 `c63f6384` + fire 의도 모드 (fork+no-persistence 포함)
**환경**: 새 Desktop 세션, `test_fire.py` 가 `--fork-session --no-session-persistence` 포함하고 발사.

**결과**:
- fire turn 이 사용자 transcript 에 **안 적힘** (의도된 cache-necromancer 동작)
- chat 의 다음 turn cache_read = 44,570 = **17,601 + 26,969 (turn 1 의 cache_create)**
- → fire 의 cache_create 27,334 은 **무시됨**

**결정적 evidence**: fork 모드에서는 fire 와 chat 의 cache 가 분리됨.

### Test 8 — 새 세션 `fba968c6` + fire 2회 + chat 사이사이 (fork 빼고)
**환경**: fork 빼고 두 번 발사 + 사이사이 chat turn.

**transcript 순서**:
```
turn 1: ''                      cache_read=17,601  cache_create=25,102
turn 2: '안녕하세요'            cache_read=17,601  cache_create=25,102
turn 3: 'No response requested' cache_read=0       cache_create=0
turn 4: '2' (fire 1+1=)         cache_read=18,833  cache_create=27,476
turn 5: '저는 Claude예요...'    cache_read=42,703  cache_create=2,453
turn 6: 'No response requested' cache_read=0       cache_create=0
turn 7: '4' (fire 2+2=)         cache_read=46,309  cache_create=41
```

**결정적 evidence** (turn 5):
```
turn 5 의 cache_read = 42,703
                    = 17,601 (chat system) + 25,102 (turn 1 의 cache_create)
                    ≠ 17,601 + 27,476 (fire turn 4 의 cache_create = 45,077)
```

→ chat turn 5 는 **turn 1 의 cache 만 hit**. fire turn 4 의 27K cache 는 무시.

**결정적 evidence** (turn 7, fire #2):
```
turn 7 의 cache_read = 46,309
                    = 18,833 (-p system) + 27,476 (fire turn 4 의 cache_create)
```

→ fire #2 는 fire #1 의 cache 정확히 hit.

## 최종 확정 사실

### 1. `-p` 모드 vs chat 모드의 system prompt 가 다름
- 공통 안정 prefix: 17,601 ~ 18,833 (Claude Code 의 일부 + 기타 안정 부분)
- 그 이후로 두 모드 prompt 가 완전히 다름

### 2. cache namespace 가 prefix 처음부터 분리
- chat cache breakpoint: chat system + transcript prefix
- fire cache breakpoint: -p system + transcript prefix
- 두 prefix 가 system 부분부터 다르므로 cache cross-mode hit 안 됨

### 3. fire 끼리는 cache 잘 hit
- fire #2 = fire #1 의 cache 정확히 hit (Test 6, 8)
- fire #2+ 의 비용 매우 작음 ($0.02 ~ $0.03)

### 4. chat 끼리는 cache 잘 hit
- chat turn N+1 = chat turn N 의 cache 정확히 hit (Test 7, 8)
- chat 자체 TTL 갱신 메커니즘 정상

### 5. fork+no-persistence 모드 효과
- ✅ 사용자 chat transcript 안 건드림 (의도된 동작)
- ❌ 사용자 chat 의 cache TTL 갱신 효과 0 (fundamental issue)

### 6. fork 빼면 transcript 에 fire turn 추가됨
- fire 의 assistant 응답 ('2', '4') 이 transcript 에 추가
- ⚠️ 그러나 `claude -c` UI 에서는 안 보임 (UI hide 메커니즘 추정)
- 부작용: chat 흐름에 fire turn 끼어들어감

### 7. non-tty silent hang 은 transcript 크기 의존
- 큰 transcript (1M+) + 활성 sid + non-tty = silent hang (Test 1, 2)
- 작은 transcript + 활성 sid + non-tty = 정상 종료 (Test 5, 8)

## 미해결 의문

1. **`claude -c` 에서 fire turn 이 안 보이는 메커니즘**
   - jsonl 에는 적혀있지만 UI 가 hide
   - turn 의 metadata / type 차이로 hide 되는 듯
   - 활용 가능성: fork 빼고 fire 해도 사용자 인지 없음

2. **chat 자체 TTL 갱신 메커니즘 정확한 동작**
   - cache hit 시점에 TTL refresh? 또는 절대 시점 만료?
   - Anthropic prompt cache 의 TTL 정책 확인 필요

3. **`-p` 와 chat 의 system prompt 정확한 차이**
   - 18K 공통 + 차이 부분
   - 어떤 환경/flag 로 동일하게 만들 수 있는지

4. **fork 된 새 sid 의 state file 등록**
   - cache-necromancer state 디렉토리에 stale file 누적 의심
   - 별도 트랙
